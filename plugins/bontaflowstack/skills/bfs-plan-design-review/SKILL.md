# BFS Plan Design Review

Load [HOST.md](../../HOST.md) for execution, state and authorization rules unless its full matching content is already loaded in this chat. Follow its hash-based read protocol.
Modes: `bfs-review`. Choose the mode from the actual request.

1. Read the brief, proposed screens, content and existing design system. Identify the primary journey and audience.
2. Walk entry, action, feedback and exit states. Include relevant empty, loading, error, success and permission states.
3. Check hierarchy, navigation, content density, component consistency, mobile layout and keyboard access.
4. Examine text contrast, focus, labels, motion preferences and whether information depends solely on color.
5. Explain each substantive issue through the user task it impairs and propose a specific change. Distinguish a preference from a usability defect.
6. Return findings and acceptance criteria for the implemented UI. Describe these as plan judgments, not measured browser results.

Consult optional presentation preferences through bfs-plan-tune when relevant; they do not decide product scope.
