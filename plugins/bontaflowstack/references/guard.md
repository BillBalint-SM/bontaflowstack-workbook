# Guard operations

Before a guard change, obtain the matching `BFS_GUARD_OBSERVED` task/workspace
marker from native PreToolUse context. A manual hook or fixture is not native
proof. Setup reports missing observation; workflow checkpoints still work.
New or changed hooks require Codex `/hooks` review; preserve host trust records.

Supported edit/patch paths obey the boundary. Recognized destructive commands
stop with an exact pending operation ID; project-root deletion is denied.
Arbitrary shell filesystem writes are outside boundary coverage; report that limit.

After the user's authorization for that specific command and target, call
`guard approve` with the pending ID, native observation and authorization quote.
Retry the unchanged tool call once within five minutes. The ID is not permission,
and the grant never overrides host permissions. A hard boundary denial requires
a corrected target or explicit boundary change.

Release clears only the boundary; command warnings remain unless the user asks
to disable both. Read status after changes to verify the result.

Read [commands](commands.md#guard) when constructing a guard core request.
