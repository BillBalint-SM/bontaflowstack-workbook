# Decisions and domain

Start from the next observable user outcome. For each unresolved point identify
the affected behavior, the evidence already available and what each answer changes.
Inspect project facts yourself; reuse accepted decisions while their basis remains
valid. Label an assumption as proposed, with its consequence, rather than accepted.

Resolve the nearest upstream choice first. Ask one material question with concrete
alternatives and effects; wait for the actual answer before dependent work. After
the answer, prune excluded branches and recompute the next useful step. A choice
with no effect on the requested result needs no question or recorded ceremony.
Retain the selected direction, actual decision source and remaining uncertainty in
the requested brief/spec or existing workflow; HOST controls persistent recording.
For dependent choices, use a compact decision list: local ID, question, blocking
decision IDs, consequence, status, chosen answer and actual source. Independent
material questions may be grouped when that reduces the user's effort.

For a term that could change an entity, owner, state or interface, inspect the
project's domain guide and its existing context/glossary/ADR sources. Trace both
meanings through the affected journey (for example login account versus billing
account). Resolve the collision before dependent design. Ask about intended product
meaning only when source and accepted decisions cannot resolve it. Use the agreed
term consistently in requirements and tests. Update the existing domain source
within authorized work; create an ADR only for a real architectural decision.
Missing optional documents alone do not block an otherwise clear task.
