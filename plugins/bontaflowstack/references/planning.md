# Verifiable tasks and dependencies

Reuse a usable task list. Otherwise split the requested outcome into small vertical
tasks, each delivering an observable path through the affected layers. One task
suffices for a small change. For each task record local ID, result, affected area,
blocking IDs, acceptance cases and verification command or observation. Local IDs
are not tracker tickets; publication follows the user's request and project guide.

Validate unique IDs, every referenced blocker, acceptance coverage and cycles before
calling the plan executable. Report the concrete missing ID or cycle path and the
affected blocked tasks. Do not silently remove an edge to manufacture readiness.

Mark a task ready only when all its blockers have verified results whose input
versions remain valid. A claimed completion, list position or stale green result
does not satisfy a blocker. Keep evidence pointers beside completion and recompute
readiness after changed inputs, failed checks or revised decisions.

For A -> B/C -> D, verified A enables B and C; D needs valid evidence from both.
Execute the resulting order within the existing workflow. The core still records
ordered skill steps; task IDs do not become fake completed workflow steps. Parallel
workers/worktrees require their separately requested procedure. Keep unresolved
product decisions visible with their affected tasks; independent work may proceed.
